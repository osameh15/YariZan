# ADR-0005 — Backend enrollment, authority and production gates

- Status: implemented for isolated development and independent review; production gate closed.
- Base: merged ADR-0004 at `c9ebb75c3d8fad98c2a685965cf6d9fc5c3a5d20`.
- Scope: NestJS modular monolith, PostgreSQL 17, unchanged desktop signed/transport profile.

## Decisions

1. Use explicit versioned SQL and typed node-postgres repositories instead of Prisma. PostgreSQL advisory/row locks, partial indexes, price-range exclusion and immutable history triggers are directly reviewable. A migration ledger verifies normalized-file hashes; an independent fresh database comparison detects catalog drift. No parallel ORM schema or automatic schema synchronization.
2. First claim has a two-minute key-bound challenge, five-minute pairing secret, browser confirmation and a second desktop proof before a one-time password claim. Username/fingerprint alone cannot claim an existing machine. PostgreSQL fingerprint/username/active-customer uniqueness and locks serialize competing claims. Initial password needs no email or SMS.
3. **This protocol does not establish genuine physical-machine ownership.** An attacker can generate a key and report an unclaimed victim fingerprint. The winner of a first-claim race is not necessarily its rightful owner. Browser/desktop secret exchange, throttling and audit reduce exposure but cannot solve hardware assurance. Production configuration always rejects startup until an independently reviewed physical/ownership assurance and dispute policy exists. No environment-ready flag promotes the source. The stock desktop enrollment provider and commercial root gate remain closed.
4. Additional profiles prove their own keys and require the existing customer's authenticated, CSRF-protected approval against the same fingerprint. They share machine UUID, customer, generation, entitlement and trial budget. No CNG key export, machine ACL changes or per-profile trial allocation. Support-assisted key rebind beyond this flow remains blocked pending independent ownership/recovery protocol review.
5. Online device authentication issues opaque, hashed 15-minute bearer credentials only after enrolled-key proof. Current status/generation is rechecked within business transactions. A former profile may retrieve only its machine's already signed REVOKED license tombstone, not ACTIVE recovery or replacement-account access. Offline certificates and paid licenses have no time lease. Credential expiration never ends a started trial or valid offline paid session.
6. Existing ADR-0004 artifact domains, claims, strict integer JCS, base64url and 64-byte P1363 signatures remain unchanged. Injectable signing management has development/test implementations only. Development keys persist in ignored runtime storage and are explicitly disposable; tests generate ephemeral keys. No production private keys are generated, embedded or approved. Commercial external custody, key rotation/retention and public-root review remain separate gates.
7. Trial and code mutations lock the device before restriction and quota/code rows. Counters include authorized customer generation. Nonces and request UUIDs have unique constraints and request digests. A committed identical retry returns its original stored signed response, including after quota exhaustion; restrictions and credential validity are checked before replay. Signing/SQL failure rolls back spending and fulfillment.
8. Customer reset advances the device generation once and tombstones the prior account. It preserves immutable finance/audit/history and stable device/SKU bans, cancels unused codes and revokes online sessions/keys/licenses. An explicitly audited trial-only reset replenishes one selected product within the existing generation and retains old nonce history. New profiles and license recovery never reset counters.
9. Cross-license-ID replacement remains blocked. Same-ID ownership-reviewed recovery produces a strictly newer signed ACTIVE decision only for the same current account/entitlement and unrestricted product. A reset account cannot recover its old entitlement through that API. The `license_replacements` table is future schema, not a working replacement endpoint or desktop snapshot migration.
10. Browser sessions use Argon2id, random hashed cookies, exact Origin/CSRF checks, rotation and logout. Support password recovery is one-use, short-lived, forces a new password and revokes old sessions; a pending reset disables old-password login. A human evidence reference plus MFA/scoped permission is required; username/HWID alone is forbidden evidence. The API records the operator's assertion; it does not automatically adjudicate evidence authenticity.
11. Admin TOTP secrets are separately encrypted; successful steps cannot replay. Sensitive operations require recent MFA, scoped RBAC, CSRF, reason, expected revision and request-bound idempotency. Plaintext activation/reset grants are delivered once; Admin retries cannot recover them from stored responses. Audit/outbox data exclude secrets. Runtime roles cannot mutate audit or schema; database owners remain trusted.
12. Outbox dispatch uses SKIP LOCKED and at-least-once event IDs. External consumers/brokers are not enabled. Future commerce tables preserve money and history but no payment, discount settlement, refund or SMS endpoints are implemented.

## Compatibility and evidence

The [compatibility report](../YARIZAN-PHASE-2-COMPATIBILITY.md) identifies every existing desktop route/field/domain. The [implemented OpenAPI snapshot](../YARIZAN-OPENAPI-BACKEND-V2.json) is extracted from actual controller routes with strict schema definitions; the earlier design OpenAPI remains a future-commerce baseline. Local tests use actual PostgreSQL and the unchanged .NET verifier/client/controller, with only identity/storage/loopback test adapters. The [engineering report](../YARIZAN-PHASE-2-REPORT.md) records exact executed results and pending physical/production evidence.

PostgreSQL lock behavior follows [official PostgreSQL 17 documentation](https://www.postgresql.org/docs/17/explicit-locking.html). Nest uses normal dependency injection and scoped authorization consistent with [official Nest authorization documentation](https://docs.nestjs.com/security/authorization). No production deployment or main modification follows from this ADR.
